# Obsidian Hermes Runtime Specification v2.0

> [!IMPORTANT]
> This document is the canonical design baseline for Obsidian Hermes v2.0.
> It specifies intended behaviour; the repository does not yet contain a
> conforming implementation.

Version 2.0 turns the v1 cron design into a smaller, typed, observable control
system. Obsidian remains the primary human interface and durable semantic
record. A deterministic bridge owns validation, reconciliation, approvals, and
mutable execution state. Hermes performs bounded work in a least-privilege
container and writes useful results back as linked living files.

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**,
and **MAY** are normative.

## 1. Decision summary

An implementation conforms to v2.0 only when it follows these decisions:

1. **Obsidian is the human control plane.** Durable intent, policy, tasks,
   approvals, context, and results are inspectable Markdown.
2. **Markdown is semantic state, not the transaction engine.** SQLite is the
   authoritative store for claims, leases, retries, run state, fencing,
   idempotency, and structured events.
3. **The bridge is the privileged controller.** It is deterministic, contains
   no model, runs outside Hermes cron, validates all resources, and reconciles
   desired state with Hermes.
4. **Tasks and runs replace chat as the durable unit of work.** A chat MAY
   create or discuss a task, but execution is always tied to a typed task and
   run.
5. **Context and skills are scoped.** A small policy core is always loaded;
   project knowledge and a narrow active skill set are retrieved on demand.
6. **The agent executes in Docker with enforced access classes.** It receives
   read/write, read-only, and hidden vault views. Prompt text is never the
   filesystem security boundary.
7. **Phase One is deliberately small.** It contains the bridge, deterministic
   router, ingest worker, queue watchdog, and daily brief. Other loops are
   deferred until the core lifecycle and recovery tests pass.
8. **Every run is traceable.** One trace identifier connects the task,
   command, run, events, output, receipt, approval, and alert.
9. **Consequential authority is explicit and exact.** Approval applies to one
   canonical plan hash, expires, and is ineffective until attested by the
   bridge.
10. **Automatic learning creates proposals.** Agents cannot silently change
    human truth, approved memory, policies, profiles, routines, or skills.

### 1.1 Goals

V2.0 is designed to provide:

- a local-first, model-independent knowledge and work environment;
- an Obsidian-first task, run, approval, and dashboard experience;
- deterministic validation before model invocation;
- immutable raw evidence with explicit provenance;
- bounded and recoverable execution;
- least-privilege filesystem, network, skill, and tool access;
- visible drift, failures, retries, costs, and pending decisions;
- safe migration from the v1 design.

### 1.2 Non-goals

Phase One does not provide:

- multiple active executors for one synchronised vault;
- autonomous external, financial, destructive, credential, or security changes;
- cross-vault federation;
- automatic deployment of generated skills or routines;
- a general durable workflow engine;
- sub-minute guarantees from Hermes cron;
- a requirement to load or index an entire vault for every run.

## 2. System model

```text
Human
  │
  ▼
Obsidian vault
  ├── read-only-to-agent intent, policy, tasks, skills and approvals
  └── agent-writable runs, evidence, outputs and proposals
  │
  ▼
Obsidian Hermes bridge
  ├── schema validation and canonical hashes
  ├── desired/actual reconciliation
  ├── approval attestation and policy enforcement
  ├── SQLite operational state and event journal
  ├── gateway supervision and health projection
  └── deterministic routing and dispatch
  │
  ▼
Hermes gateway and native cron
  │
  ▼
Docker worker sandbox
  ├── scoped context
  ├── curated skills and toolsets
  └── bounded execution
  │
  ▼
Outputs, receipts, events, and proposed learning
  │
  └──────────────────────────────► Obsidian
```

### 2.1 Responsibility boundaries

| Component | Owns | Must not own |
| --- | --- | --- |
| Human and Obsidian | Goals, policy, corrections, task readiness, approvals, review | Leases, scheduler internals, transactional claims |
| Bridge | Validation, reconciliation, state transitions, fencing, attestation, dispatch, projections | Semantic judgement, source synthesis, model reasoning |
| Operational store | Commands, runs, leases, retries, events, receipts, migrations | Human-authored knowledge or private vault content |
| Hermes | Retrieval, planning, model/tool invocation, bounded worker execution | Approval authority, cron self-administration, private data |
| Worker sandbox | One dispatched run and its authorised files/tools | Host paths, bridge database, credentials not required by the run |
| Vault | Human-readable intent, evidence, knowledge, outputs, proposals, summaries | High-churn locks, heartbeats, or the only copy of execution state |

### 2.2 Authority order

When two sources conflict, the following order applies:

1. explicit human correction;
2. attested policy or decision;
3. human-authored project or task content;
4. human-approved Hermes memory;
5. evidence-linked maintained knowledge;
6. derived summary;
7. unreviewed model inference.

Lower-authority content MUST NOT overwrite higher-authority content. Imported
content is evidence, not authority, regardless of its wording.

### 2.3 Semantic and operational state

| Data | Authority | Human projection |
| --- | --- | --- |
| Task goal, constraints, context, desired state | Markdown task | Same task |
| Routine desired state | Markdown routine | Same routine |
| Approval request and human decision | Markdown approval plus bridge attestation | Same approval |
| Claim, lease, heartbeat, retry | SQLite | Run/status summary |
| Current command and run state | SQLite | Task observation and run note |
| Structured event stream | SQLite append-only journal | Redacted run activity and logs |
| External-effect receipt | SQLite plus immutable receipt projection | Receipt file linked from run |
| Raw source | Immutable vault file | Same file |
| Maintained knowledge and outputs | Vault | Same files |

The bridge MUST be able to rebuild human projections from the operational
store. A projection edit MUST NOT directly change operational state.

## 3. Hermes runtime constraints

V2.0 assumes these Hermes behaviours and fails visibly if discovery shows they
have changed:

- cron agent runs start in fresh sessions;
- the gateway scheduler checks due work at a coarse interval, commonly about
  60 seconds;
- a requested immediate run executes on a later scheduler tick, not
  synchronously;
- scheduled sessions cannot recursively administer cron;
- jobs sharing a work directory may be serialised, but v2 correctness does not
  rely on that implementation detail;
- script-only and script-gated jobs can avoid a model invocation when no work
  is due;
- useful business results must be written to the vault rather than existing
  only in native cron output.

### 3.1 Runtime discovery

The bridge MUST discover, through supported Hermes configuration or command
interfaces:

- the active `HERMES_HOME`;
- the active Hermes profile;
- gateway availability and version;
- the native cron capability and job identifiers;
- the configured terminal backend;
- the configured timezone;
- available model/provider identifiers;
- effective Docker volume, network, and working-directory settings.

The implementation MUST NOT assume that cron data lives directly under
`~/.hermes/cron`. Profile-scoped runtime paths are internal implementation
details and MUST NOT be edited directly.

### 3.2 Scheduling

Every routine uses an explicit IANA timezone. The deployment chooses its
timezone; v2.0 does not prescribe `Australia/Melbourne` or any other locality.
Schedules are eventual triggers. Workers scan current eligible state in bounded
batches and MUST NOT assume one trigger equals one event.

### 3.3 Model pinning

Production agent routines MUST pin a provider and model profile. A missing or
invalid pin fails closed with visible drift. Global model changes MUST NOT
silently change an existing routine.

## 4. Vault and filesystem model

### 4.1 Required access zones

The host vault contains three top-level zones:

```text
Hermes-Vault/
├── ReadWrite/
├── ReadOnly/
└── Private/
```

Their effective worker permissions are:

| Zone | Worker view | Intended content |
| --- | --- | --- |
| `ReadWrite` | Read, create, modify, rename, delete | Inbox, runs, raw evidence, maintained knowledge, outputs, proposals, projections |
| `ReadOnly` | Read and search only | Human truth, tasks, policies, profiles, approved skills, routines, approvals |
| `Private` | Empty read-only mask; real entries invisible | Content that must never enter agent context |

`ReadOnly` describes the container view. The human and bridge MAY update its
host source. `Private` is not an agent context tier; it is absent.

Folder names below the access zones are defaults, not security controls. A
deployment MAY map equivalent existing folders through configuration, but each
configured path has exactly one access class.

Workers write result manifests only to their allocated directory under
`ReadWrite/99 Staging/`. The bridge validates and consumes those manifests,
then writes dispatches, receipts, status, logs, and dead-letter projections
under `ReadOnly/99 System/`. A worker can read those projections but cannot
forge or delete the human-visible audit surface.

### 4.3 Container mounts

The preferred configuration mounts the zones independently:

```yaml
terminal:
  backend: docker
  docker_mount_cwd_to_workspace: false
  docker_volumes:
    - "<HOST_RW>:/workspace/obsidian/ReadWrite"
    - "<HOST_RO>:/workspace/obsidian/ReadOnly:ro"
    - "<HOST_MASK>:/workspace/obsidian/Private:ro"
```

`HOST_MASK` is an empty directory outside the vault. It MUST NOT be a symlink
to `HOST_PRIVATE`. `HOST_PRIVATE` MUST NOT appear in any worker mount.

The required worker-visible paths are:

```text
OBSIDIAN_VAULT_PATH=/workspace/obsidian
READ_WRITE_ROOT=/workspace/obsidian/ReadWrite
READ_ONLY_ROOT=/workspace/obsidian/ReadOnly
PRIVATE_MASK_ROOT=/workspace/obsidian/Private
```

Tools receive resolved absolute container paths, never literal environment
variable expressions and never host paths.

A parent-vault read/write mount with read-only and private overlays MAY be used
only when the operator has audited every additional root entry. In particular,
an accessible `.git` directory can reveal masked private content through Git
history. Independent zone mounts are therefore preferred.

### 4.4 Docker hardening

Worker containers MUST NOT receive:

- privileged mode or `CAP_SYS_ADMIN`;
- the Docker or container-runtime socket;
- host PID, device, or network namespaces;
- `/`, a home directory, `/etc`, SSH files, browser profiles, password stores,
  cloud credential directories, or unrelated repositories;
- the bridge database, signing keys, or full host environment;
- a writable bind mount that contains `ReadOnly` or `Private` through another
  path.

Network is disabled by default. A task that needs network access uses an
enforced destination allowlist or a constrained proxy. A frontmatter label or
prompt alone is not network enforcement.

### 4.5 Trusted instructions

The bridge assembles each worker prompt from the approved agent profile and
`ReadOnly/Policies`. If Hermes requires workdir instruction files, the bridge
MUST provide read-only copies or bind mounts. An agent-writable `AGENTS.md` or
`SCHEMA.md` is a cache only and MUST NOT be trusted for authorisation.

## 5. Resource and schema rules

### 5.1 Executable schemas

Every resource kind has a strict, machine-executable schema. A conforming
implementation ships versioned JSON Schema or equivalent validation models for:

```text
hermes.task/v2
hermes.run/v2
hermes.routine/v2
hermes.control/v2
hermes.approval/v2
hermes.agent/v2
hermes.skill/v2
hermes.raw-source/v2
hermes.receipt/v2
hermes.status/v2
hermes.event/v2
```

Validation occurs before reconciliation, routing, claiming, approval, or model
invocation. Unknown operations, states, fields, or enum values fail closed.
Implementations MAY permit extensions only inside an explicit `extensions`
mapping whose keys begin with a registered namespace.

### 5.2 Frontmatter parsing

Resource notes:

- are UTF-8 Markdown with exactly one leading YAML frontmatter document;
- reject duplicate keys, aliases, custom tags, non-string map keys, and
  multiple YAML documents;
- use RFC 3339 timestamps with offsets;
- use relative vault paths or stable IDs in resources, not host paths;
- use an integer `revision` that increases for each human-owned specification
  change;
- use a required `schema_version: 2` in addition to the full `schema` name;
- preserve stable IDs across renames and moves.

Examples containing `...` or uppercase placeholders illustrate a contract and
are not conformance fixtures. Implementations MUST ship complete valid fixtures
for every executable schema.

### 5.3 Identifiers

System-generated resource and operational IDs use a type prefix and a
26-character Crockford ULID:

```text
task_01K2...
cmd_01K2...
run_01K2...
control_01K2...
approval_01K2...
receipt_01K2...
event_01K2...
trace_01K2...
span_01K2...
```

Human-maintained catalogue IDs for projects, routines, agent profiles, and
skills are stable lowercase slugs matching:

```text
[a-z][a-z0-9]*(?:-[a-z0-9]+)*
```

Content-derived source IDs use `src_sha256_<64-lowercase-hex>`. IDs are
immutable and unique within their namespace. Paths and titles are not
identities.

### 5.4 Canonical hashes

The bridge computes hashes as follows:

1. parse with the safe YAML profile;
2. validate against the exact schema version;
3. select the fields defined by the hash contract;
4. encode mappings with lexicographically sorted keys as UTF-8 JSON without
   insignificant whitespace;
5. preserve array order;
6. normalise Markdown body line endings to LF and one final newline when the
   body belongs to the hash contract;
7. calculate SHA-256 and format it as `sha256:<lowercase-hex>`.

Generated observation, trace, and attestation fields are excluded from a
resource specification hash. A plan hash includes the complete ordered action
list, arguments, permissions, budgets, expected outputs, and idempotency keys.
A material change creates a new hash and invalidates prior approval.

## 6. Human-facing resources

### 6.1 Task

A task is the durable human contract. Authoritative tasks live under
`ReadOnly/70 Tasks/`; agent-created suggestions live under
`ReadWrite/70 Tasks/Proposals/` and are not executable.

```yaml
---
schema: hermes.task/v2
schema_version: 2
id: task_01K2ABCDEFGHJKMNPQRSTVWXYZ
revision: 1
title: Ingest the supplied architecture source
desired_state: ready
operation: source.ingest
mode: execute
priority: 50
created_at: 2026-08-11T03:09:00Z
requested_by: user:local-owner
project_ref: architecture
agent_profile: researcher

goal: Preserve, analyse, and index the supplied source.
context_refs:
  - architecture
context_roots:
  - ReadOnly/10 Projects/Architecture
  - ReadWrite/30 Knowledge
skills:
  - source-ingestion

inputs:
  - type: url
    value: https://example.invalid/source

permissions:
  network:
    mode: allowlist
    destinations:
      - example.invalid
  read:
    - ReadOnly/10 Projects/Architecture/**
    - ReadWrite/30 Knowledge/**
  write:
    - ReadWrite/30 Knowledge/**
    - ReadWrite/06 Outputs/**
  external_effects: deny
  destructive_write: deny

budgets:
  max_runtime_minutes: 10
  max_input_tokens: 50000
  max_output_tokens: 10000
  max_network_requests: 10

approval_policy:
  required_before: []

completion_criteria:
  - Raw content is preserved with a content hash.
  - Maintained knowledge links to the raw source.
  - The run has a terminal receipt.

output:
  kind: source-summary
  path: ReadWrite/06 Outputs/Reports/

observed:
  generation: 0
  state: pending
  active_run_id:
  last_terminal_run_id:
  last_error:
  reconciled_at:
---
```

Human-owned fields end before `observed`. The bridge owns `observed` and MAY
render it into the task. Editing `observed` does not authorise a transition.

Allowed `desired_state` values are:

```text
draft
ready
paused
cancelled
```

The bridge reports these observed task states:

```text
pending
invalid
queued
running
approval_required
blocked
completed
failed
cancelled
```

### 6.2 Task modes

`mode: execute` permits the effects allowed by the task. `mode: dry-run`
permits validation, bounded reads, and creation of a plan artifact only. It
MUST NOT perform target vault mutations or external effects. The bridge records
the resulting plan hash and changes the observed state to
`approval_required` when execution needs approval.

### 6.3 Run

A run is one attempt to execute one immutable task generation. Run notes under
`ReadWrite/80 Runs/` are bridge-rendered projections of operational state.

```yaml
---
schema: hermes.run/v2
schema_version: 2
id: run_01K2ABCDEFGHJKMNPQRSTVWXY1
task_id: task_01K2ABCDEFGHJKMNPQRSTVWXYZ
task_generation: 1
command_id: cmd_01K2ABCDEFGHJKMNPQRSTVWXY2
trace_id: trace_01K2ABCDEFGHJKMNPQRSTVWXY3
state: running
agent_profile: researcher
model_profile: reasoning-pinned
created_at: 2026-08-11T03:10:00Z
started_at: 2026-08-11T03:11:02Z
finished_at:
context_manifest:
  - ref: architecture
    reason: Explicit task context
skills_used:
  - source-ingestion
usage:
  input_tokens: 0
  output_tokens: 0
  network_requests: 0
outputs: []
approval_ids: []
receipt_id:
last_checkpoint:
error:
---
```

The bridge owns run state. Worker output is accepted through the dispatch result
contract and then rendered into the note. The run activity view MUST identify:

- the plan and current step;
- context selected and why;
- skills and tools used;
- files created or changed;
- external requests and side effects;
- time, token, API, and monetary usage when available;
- warnings, retries, and failure class;
- outputs, receipt, and proposed learning.

### 6.4 Routine

Authoritative routine notes live under `ReadOnly/90 Automations/`.

```yaml
---
schema: hermes.routine/v2
schema_version: 2
id: ingest-worker
revision: 1
desired_state: active
name: obsidian/knowledge/ingest-worker

schedule:
  expression: "every 5m"
  timezone: Etc/UTC

execution:
  mode: script-gated-agent
  capability: ingest
  workdir: /workspace/obsidian
  script: obsidian-ingest-gate
  agent_profile: researcher
  provider: PINNED_PROVIDER
  model: PINNED_MODEL

limits:
  max_items_per_run: 3
  max_runtime_minutes: 10

approval:
  required_for_change: true
  approval_id:
  approved_spec_hash: sha256:...

observed:
  state: pending
  native_job_id:
  applied_revision:
  applied_spec_hash:
  last_reconciled_at:
  last_error:
---
```

Routine schemas contain logical capabilities, not host script paths or Hermes
internal storage paths. The bridge resolves approved capability names through
its deployment configuration.

Allowed routine `desired_state` values are:

```text
draft
active
paused
absent
```

`absent` is an explicit, approved request to remove the native job. Deleting or
moving a routine note does not request removal; it creates drift and leaves the
last known-safe native state unchanged.

Observed routine states are:

```text
pending
in_sync
out_of_sync
reconciling
paused
degraded
invalid
blocked
absent
```

### 6.5 Skill and agent profile

Authoritative agent profiles live under `ReadOnly/50 Agents/` and define the
maximum prompt, model, context, skill, permission, and budget envelope for one
worker role.

```yaml
---
schema: hermes.agent/v2
schema_version: 2
id: researcher
revision: 1
status: approved
purpose: Perform evidence-linked research and source ingestion.
prompt_sources:
  - ReadOnly/Policies/AGENTS.md
  - ReadOnly/Policies/SCHEMA.md
model:
  provider: PINNED_PROVIDER
  name: PINNED_MODEL
allowed_skills:
  - source-ingestion
context_roots_maximum:
  - ReadOnly/10 Projects/**
  - ReadOnly/40 Memory/**
  - ReadWrite/30 Knowledge/**
permissions_maximum:
  network: allowlist
  read:
    - ReadOnly/**
    - ReadWrite/30 Knowledge/**
  write:
    - ReadWrite/30 Knowledge/**
    - ReadWrite/06 Outputs/**
    - ReadWrite/99 Staging/**
  external_effects: deny
  destructive_write: deny
budgets_maximum:
  runtime_minutes: 15
  input_tokens: 75000
  output_tokens: 15000
  network_requests: 20
review_after: 2026-11-01
---
```

Prompt sources MUST be in an agent-read-only zone. For scheduled work, a
routine's provider/model pin MUST match a tuple permitted by its agent profile;
otherwise the routine is blocked. For an authenticated ad-hoc dispatch without
a routine pin, the approved agent profile's exact pin is used. If neither path
produces one exact provider/model tuple, dispatch fails closed.

The full skill catalogue MAY be visible in Obsidian, but each run activates
only the task/profile intersection.

```yaml
---
schema: hermes.skill/v2
schema_version: 2
id: source-ingestion
revision: 1
status: approved
purpose: Preserve and index an external source with provenance.
triggers:
  - source ingestion
permissions:
  network_maximum: allowlist
  read:
    - ReadOnly/10 Projects/**
    - ReadWrite/30 Knowledge/**
  write:
    - ReadWrite/30 Knowledge/**
inputs:
  - source
outputs:
  - raw-source
  - source-summary
agents:
  - researcher
review_after: 2026-11-01
---
```

A task cannot expand a profile or skill permission. Effective permission is the
intersection of deployment, routine, profile, skill, task, and approval
constraints. Descriptions MUST be discriminative. Overlapping skills are
narrowed, ordered, merged, or disabled.

### 6.6 Approval

Approval notes live under `ReadOnly/95 Approvals/`.

```yaml
---
schema: hermes.approval/v2
schema_version: 2
id: approval_01K2ABCDEFGHJKMNPQRSTVWXY4
revision: 1
trace_id: trace_01K2ABCDEFGHJKMNPQRSTVWXY3
action_class: external_write
risk_tier: 3
subject:
  type: task-plan
  task_id: task_01K2ABCDEFGHJKMNPQRSTVWXYZ
  run_id: run_01K2ABCDEFGHJKMNPQRSTVWXY1
  task_generation: 1
  hash_kind: plan
  hash: sha256:...
requested_at: 2026-08-11T03:15:00Z
expires_at: 2026-08-12T03:15:00Z
decision: pending
decided_by:
decided_at:
attestation:
  method:
  key_id:
  signature:
---

## Proposed action

Describe the exact effect, destination, inputs, and rollback limits.

## Evidence

- [[Linked plan]]

## Human decision

Use the bridge approval command or approved Obsidian integration.
```

Changing `decision` in Markdown alone is not authority. The bridge validates
the decision through an authenticated local action or signature and writes an
attestation over the approval ID, decision, complete subject, expiry, and
approver.

An approval subject is exactly one of:

- `task-plan`, containing task ID, run ID, task generation, and plan hash; or
- `routine-spec`, containing routine ID, revision, and specification hash.

```yaml
subject:
  type: routine-spec
  routine_id: ingest-worker
  revision: 1
  hash_kind: specification
  hash: sha256:...
```

For a routine change, the approval uses `action_class: routine_change`, the
routine note's `approval_id` references it, and `approved_spec_hash` MUST equal
the attested subject hash. A missing, expired, or mismatched approval leaves
the routine out of sync. Routine authority changes use a separate signed
approval and MUST NOT be batched.

| Risk | Examples | Requirement |
| --- | --- | --- |
| 0 | Local read, search, analysis | Automatic within scope |
| 1 | Reversible write in `ReadWrite` | Task grant; receipt |
| 2 | Allowlisted network read; threshold-exceeding reversible vault change | Explicit task grant; bulk changes also require exact-plan approval |
| 3 | Message, publication, external mutation | Exact-plan approval and attestation |
| 4 | Financial, destructive, credential, security, or runtime-authority change | Separate signed approval per effect; no batching |

Phase One workers do not execute Tier 3 or Tier 4 business effects. Phase One
MAY create a Tier 2 `bulk_vault_write` approval when an ingest plan exceeds its
change threshold. Bridge reconciliation of routine specifications remains a
Tier 4 control-plane action.

### 6.7 Control request

Attested one-shot operator requests live under `ReadOnly/99 Control/`.

```yaml
---
schema: hermes.control/v2
schema_version: 2
id: control_01K2ABCDEFGHJKMNPQRSTVWXY8
revision: 1
operation: task.snooze
target:
  type: task
  id: task_01K2ABCDEFGHJKMNPQRSTVWXYZ
parameters:
  not_before: 2026-08-11T05:00:00Z
requested_by: user:local-owner
created_at: 2026-08-11T03:20:00Z
expires_at: 2026-08-11T03:30:00Z
attestation:
  method: local-bridge
  key_id: local-owner
  signature: SIGNATURE_PLACEHOLDER
observed:
  state: pending
  applied_at:
  result_event_id:
  error:
---
```

The closed Phase One control vocabulary is:

```text
task.cancel
task.retry
task.snooze
routine.run-once
system.reconcile
system.validate
system.verify-mounts
```

The attestation covers the complete control specification hash and expiry.
Markdown edits invalidate it. The bridge owns `observed`, applies each control
ID at most once, and records a result event. Desired routine lifecycle changes
use `desired_state` plus routine-spec approval rather than one-shot control
requests. Control resources never map to direct edits of Hermes internal
storage.

## 7. Operational store and event model

### 7.1 Store requirements

The bridge owns a profile-scoped SQLite database outside the synced vault and
outside all worker mounts. It MUST:

- enable foreign-key enforcement;
- use transactions for every state transition;
- provide crash-safe journaling;
- apply ordered, reversible schema migrations where possible;
- retain migration and application versions;
- enforce one current lease per command;
- make idempotency keys unique;
- persist an event in the same transaction as each state change, or use a
  transactional outbox;
- support consistent backup and restore with the vault;
- never store secret values or private vault content.

Required logical records are:

```text
resources
commands
runs
leases
approvals
receipts
events
outbox
fence
migrations
```

This list defines behaviour, not table names.

### 7.2 Command state machine

The router compiles a validated task generation into an immutable operational
command:

```text
queued
  │
  ▼
validated
  │
  ▼
claimed
  │
  ▼
running
  ├──────────────► awaiting_approval ───► queued
  ├──────────────► retry_scheduled ─────► queued
  ▼
verifying
  │
  ▼
completed
```

Terminal and exceptional states are:

```text
blocked
failed
cancelled
dead_letter
superseded
```

| Transition | Authority |
| --- | --- |
| task `ready` → command `queued` | Bridge |
| `queued` → `validated` | Deterministic router |
| `validated` → `claimed` | Transactional dispatcher |
| `claimed` → `running` | Worker launcher |
| `running` → `awaiting_approval` | Bridge after validated plan |
| `awaiting_approval` → `queued` | Bridge after valid attestation |
| `running` → `verifying` | Worker result accepted by bridge |
| `verifying` → `completed` | Deterministic acceptance checks |
| eligible → `retry_scheduled` | Bridge recovery policy |
| due `retry_scheduled` → `queued` | Bridge |
| non-terminal → `cancelled` | Bridge from authenticated human intent |
| old generation → `superseded` | Bridge after a newer task generation is accepted |
| retry exhausted → `dead_letter` | Watchdog |

A model cannot directly transition operational state.

### 7.3 Claim and lease

Claims are conditional database updates. A claim succeeds only when:

```text
state == validated
not_before <= now
no live lease exists
task generation is still current
executor fence token is current
```

The lease records owner, issue time, expiry, heartbeat, run ID, and fence
epoch. Workers checkpoint after each durable phase. The bridge renews or
records heartbeats through its narrow dispatch interface.

An expired lease is recovered as follows:

- no durable effect: return to `validated`;
- safe checkpoint and idempotent continuation: set `retry_scheduled`;
- uncertain effect: set `blocked`;
- repeated stale recovery beyond policy: set `dead_letter`.

An uncertain external effect is never retried automatically.

### 7.4 Retry and snooze

Retry state belongs to the command, not the cron trigger. It includes attempt,
maximum attempts, failure class, `not_before`, last error, and prior run IDs.
The default delays are 2, 10, and 30 minutes with bounded jitter. Operators MAY
snooze work by moving `not_before` forward through an authenticated bridge
action.

### 7.5 Event envelope

Every material transition emits:

```yaml
schema: hermes.event/v2
schema_version: 2
event_id: event_01K2ABCDEFGHJKMNPQRSTVWXY5
trace_id: trace_01K2ABCDEFGHJKMNPQRSTVWXY3
span_id: span_01K2ABCDEFGHJKMNPQRSTVWXY6
parent_span_id:
sequence: 12
occurred_at: 2026-08-11T03:16:00Z
type: command.claimed
actor: bridge:local
task_id: task_01K2ABCDEFGHJKMNPQRSTVWXYZ
command_id: cmd_01K2ABCDEFGHJKMNPQRSTVWXY2
run_id: run_01K2ABCDEFGHJKMNPQRSTVWXY1
outcome: success
data:
  worker_class: ingest
```

Event payloads contain identifiers and bounded metadata, not prompts, raw
source bodies, secret values, or private content. Sequence numbers are
monotonic within a trace. Projections MAY omit events but MUST preserve links
to the complete redacted trace.

### 7.6 Receipts

Every terminal command has a receipt. Every external step has its own unique
idempotency key:

```json
{
  "schema": "hermes.receipt/v2",
  "schema_version": 2,
  "receipt_id": "receipt_01K2ABCDEFGHJKMNPQRSTVWXY7",
  "trace_id": "trace_01K2ABCDEFGHJKMNPQRSTVWXY3",
  "command_id": "cmd_01K2ABCDEFGHJKMNPQRSTVWXY2",
  "run_id": "run_01K2ABCDEFGHJKMNPQRSTVWXY1",
  "step_id": "preserve-source",
  "idempotency_key": "cmd_01K2ABCDEFGHJKMNPQRSTVWXY2:preserve-source:v1",
  "status": "completed",
  "completed_at": "2026-08-11T03:17:00Z",
  "outputs": ["ReadWrite/30 Knowledge/raw/src_sha256_0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef.md"],
  "content_hash": "sha256:..."
}
```

The execution guarantee is at-least-once dispatch with idempotent effects, not
exactly-once delivery.

## 8. Bridge specification

### 8.1 Process and privilege

The bridge is a long-running, non-LLM service under a dedicated non-root
account. It runs outside Hermes cron and is the only Obsidian Hermes component
authorised to:

- reconcile native cron jobs;
- mutate operational state;
- attest approvals;
- issue worker dispatch credentials;
- update bridge-owned Markdown projections;
- promote approved memory, task, routine, or skill proposals;
- report and optionally request gateway restart through an approved service
  manager integration.

It MUST NOT have unrestricted root, Docker daemon, private-vault, or secret
manager access.

### 8.2 Startup protocol

On startup the bridge:

1. resolves and validates host and container path configuration;
2. verifies that the operational database is outside worker mounts;
3. acquires the single-executor lock and increments the fence epoch;
4. applies or refuses operational-store migrations;
5. discovers the active Hermes profile and capabilities;
6. validates effective Docker mounts and forbidden exposure;
7. verifies schema and policy bundle hashes;
8. loads all desired resources with strict validation;
9. compares desired, recorded, and native states;
10. emits startup and drift events;
11. enters reconciliation only if safety checks pass.

Failure before step 11 leaves execution paused.

### 8.3 Reconciliation loop

The bridge uses filesystem notifications for responsiveness and a full
periodic rescan for reliability. Notifications are hints; the rescan is the
repair mechanism.

For each resource generation it:

1. reads through a stable file handle;
2. rejects symlinks or paths outside the configured zone;
3. parses and validates the schema;
4. verifies field ownership, revision, and approval;
5. computes the specification hash;
6. reads current operational and native state;
7. computes a deterministic action;
8. records intent and event transactionally;
9. invokes the supported Hermes operation when required;
10. records the result and renders projections atomically.

Whole-file projections use temporary-file, flush, and same-filesystem rename.
The bridge never edits Hermes internal job files.

### 8.4 Routine reconciliation

| Desired condition | Actual condition | Action |
| --- | --- | --- |
| `active` | absent | Create after validation and approval |
| `active` | matching hash | No-op |
| `active` | different hash | Mark out of sync; update only with approval |
| `paused` | active | Pause |
| `active` | paused | Resume |
| `absent` | exists | Remove only with explicit approval |
| invalid | any | Block and retain last known-safe state |
| model unavailable | any | Degrade; do not silently repin |

Native job IDs are authoritative runtime identities. Human-readable names are
not assumed unique.

### 8.5 Single-executor fencing

Phase One permits exactly one active bridge/executor per vault. A local OS lock
alone is insufficient for a synced multi-machine vault. A deployment that
enables multiple potential hosts MUST provide a tested external lease with
monotonic fencing tokens. If exclusive ownership cannot be proven, all
dispatch stops and status becomes `blocked`.

The bridge detects sync-conflict files and conflicting bridge identities. It
MUST NOT resolve semantic conflicts automatically.

### 8.6 Dispatch interface

The bridge exposes a narrow, authenticated dispatch contract. It MAY use a
local API, one-time signed envelope, or equivalent mechanism, but it MUST:

- claim work transactionally before revealing it to a worker;
- bind the dispatch to one run, trace, task generation, fence epoch, and
  expiry;
- include only the context paths and permissions needed for that run;
- prevent a worker from claiming arbitrary commands or changing another run;
- validate checkpoints and result manifests;
- revoke or expire credentials after the run;
- avoid exposing the operational database or bridge signing key.

Files under `ReadOnly/99 System/Dispatch/` are projections or signed
envelopes, not authority by themselves. Each dispatch allocates exactly one
`ReadWrite/99 Staging/<run-id>/` result directory as a protocol write
capability that does not authorise target changes. The bridge rejects manifests
from any other run or location.

### 8.7 Gateway supervision

The bridge observes gateway and scheduler health independently of Hermes cron.
An operating-system service manager SHOULD own restart policy. The bridge MAY
request a configured restart, but it records each request and MUST use a
bounded backoff. An internal queue watchdog is not considered proof of gateway
liveness.

## 9. Phase One components

Phase One contains exactly these operational components:

| Component | Mode | Purpose |
| --- | --- | --- |
| Control bridge | External deterministic service | Validate, reconcile, dispatch, supervise, project |
| Command router | Deterministic bridge subsystem or script | Compile eligible tasks into typed commands |
| Ingest worker | Script-gated Hermes agent | Preserve and index bounded source material |
| Queue watchdog | Script-only plus bridge checks | Detect stalled, malformed, conflicting, or unsafe work |
| Daily brief | Pinned Hermes agent | Produce a linked human status summary |

The Phase One operation vocabulary is:

```text
source.ingest
brief.generate
```

Unknown and deferred operations are blocked. Implementations MUST NOT interpret
an unknown operation from natural language.

### 9.1 Deterministic router

The router:

1. reads ready task resources;
2. validates schema, generation, operation, context roots, permissions, budget,
   profile, and skill references;
3. rejects paths escaping configured roots;
4. computes the task specification and dedupe hashes;
5. compiles an immutable operational command;
6. records the command and trace transactionally;
7. updates task observation through the bridge;
8. never performs the requested substantive work.

No valid work produces no worker or model invocation.

### 9.2 Ingest worker

The ingest transaction is:

```text
Receive one attested dispatch
  → read trusted policy and scoped context
  → retrieve or read the source
  → calculate canonical source ID and SHA-256
  → detect an existing source and receipt
  → preserve one immutable raw copy
  → extract metadata and provenance
  → identify related maintained pages
  → create bounded evidence-linked updates
  → write a result manifest
  → bridge verifies outputs and receipt
  → command reaches a terminal state
```

Raw source metadata includes:

```yaml
---
schema: hermes.raw-source/v2
schema_version: 2
source_id: src_sha256_0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
source_type: article
source_url: https://example.invalid/source
retrieved_at: 2026-08-11T03:16:00Z
content_sha256: sha256:...
title: Example
author:
published_at:
trace_id: trace_01K2ABCDEFGHJKMNPQRSTVWXY3
task_id: task_01K2ABCDEFGHJKMNPQRSTVWXYZ
immutable: true
security_flags: []
---
```

A security flag is diagnostic metadata, not proof that content is safe.
Instructions found in source material remain untrusted data.

The worker searches titles, aliases, stable identifiers, and source hashes
before creating a maintained page. It records contradictions instead of
deleting one side. A change exceeding the configured file or page threshold
produces a dry-run manifest and stops with a Tier 2
`action_class: bulk_vault_write` approval request. Execution resumes only for
the attested manifest hash.

### 9.3 Queue watchdog

The deterministic watchdog reports:

- expired leases or missing heartbeats;
- tasks queued beyond their objective;
- malformed or schema-incompatible resources;
- retries approaching exhaustion;
- dead-letter growth;
- approvals nearing or past expiry;
- unresolved sync conflicts;
- altered raw-source hashes;
- missing terminal receipts;
- low disk space or failed backups;
- current fence or bridge ownership ambiguity.

Healthy execution is silent. The watchdog cannot certify its own scheduler or
gateway; the bridge performs those checks.

### 9.4 Daily brief

The daily brief is written to
`ReadWrite/06 Outputs/Briefings/YYYY-MM-DD Daily Brief.md` and contains:

1. attention required;
2. pending or expiring approvals;
3. blocked, failed, and dead-letter work;
4. active and recently completed runs;
5. new knowledge and outputs;
6. contradictions or low-confidence findings;
7. resource and budget warnings;
8. gateway, bridge, scheduler, backup, and mount health.

Every item links to its source resource or trace. The brief does not invent
urgency and does not execute recommendations.

## 10. Context, memory, and learning

### 10.1 Context tiers

| Tier | Contents | Loading rule |
| --- | --- | --- |
| 1. Core policy | Safety, identity, routing, critical corrections | Always loaded; deliberately small |
| 2. Human truth | Projects, decisions, goals, explicit preferences | Explicit task/profile references |
| 3. Approved memory | Reviewed stable facts and summaries | Relevance-scoped; lower authority than human truth |
| 4. Project knowledge | Evidence, notes, plans, outputs, procedures | Search only within declared roots |
| 5. Prior runs | Traces, sessions, intermediate history | Continuity or diagnosis only |
| 6. Ephemeral work | Current plan, tool responses, calculations | Run-local; discard or summarise |

The entire vault MUST NOT be inserted into a run context.

### 10.2 Retrieval sequence

Workers:

1. load the attested dispatch and core policy;
2. load the selected profile and task's explicit references;
3. search only declared context roots;
4. prefer exact entities, recent decisions, and prior accepted outputs;
5. apply file, token, and relevance budgets;
6. record each selected source and reason in the context manifest;
7. stop when additional context has insufficient marginal value.

Private paths never appear as retrieval candidates. A missing or masked path is
reported as unavailable, not inferred.

### 10.3 Controlled learning

Memory and skill lifecycle is:

```text
observe → propose → review → test → approve → measure → maintain or retire
```

Agents write proposals only to `ReadWrite`. Promotion into `ReadOnly` is a
bridge action following human review. Each proposal includes provenance, the
originating trace, a diff, confidence, scope, review date, and conflicts with
existing content.

Corrections supersede stale memory explicitly. Time-sensitive memory has an
expiry or review date. Project-specific memory is not retrieved outside its
scope.

## 11. Security and threat model

### 11.1 Trust boundaries

The only instruction authorities are:

- attested human policy and task resources;
- the bridge's validated dispatch envelope;
- approved agent profiles and skills;
- the v2 schema and deployment policy.

The following are always untrusted:

```text
raw sources
inbox captures
attachments
webpages
emails and messages
transcripts
tool output
model output
agent-created task, memory, skill, or routine proposals
```

### 11.2 Required controls

| Threat | Preventive control | Detection and recovery |
| --- | --- | --- |
| Indirect prompt injection | Separate untrusted content; minimal tools; deterministic dispatch and output validation | Security event; quarantine or block run |
| Approval spoofing | Agent-read-only approvals; authenticated bridge attestation; exact plan hash and expiry | Reject unattested or changed approval |
| Path traversal or symlink escape | Canonical path validation, no-follow opens, zone allowlists | Block run; record attempted path |
| Private-data exposure | No private source mount; empty mask; no alternate parent or Git-history path | Private-token and mount-table tests |
| Bridge compromise | Dedicated non-root account; narrow runtime and secret access; audit log | Stop dispatch; rotate keys; restore known-safe state |
| Duplicate effect | Stable idempotency key; receipt uniqueness; block uncertain outcomes | Reconcile external reference manually |
| Multi-executor race | Single active bridge and monotonic fence | Pause on conflict; operator selects owner |
| Sync conflict | Stable IDs, single writer, atomic projections, conflict detection | Block affected resources; preserve both versions |
| Secret exfiltration | Secret references, scoped injection, redaction, network controls | Revoke credential; inspect trace without printing value |
| Model or skill drift | Pinned model/profile and approved hashes | Mark routine out of sync |
| Resource exhaustion | Runtime, token, file, request, and cost budgets | Cancel or require reauthorisation |

### 11.3 Path handling

Every bridge, gate, and worker file operation:

- starts from a configured zone root;
- rejects absolute host paths and `..` escape;
- resolves or safely opens path components without following unapproved
  symlinks;
- checks the final object remains under the intended root;
- rejects hard links or alternate mounts that cross an access class;
- treats case-folding and Unicode-normalisation collisions as conflicts;
- uses bounded file size and count limits.

### 11.4 Secrets

Secrets never appear in tasks, prompts, vault notes, events, receipts, logs, or
reports. Resources use opaque references such as:

```yaml
credential_ref: secret://research/read-only-token
```

The bridge resolves only approved references and injects a credential only
into the run that needs it. Reports list variable or reference names, never
values.

### 11.5 Git and backups

Before the first agent write, the operator:

1. inspects existing Git state;
2. preserves all user changes;
3. creates a local baseline checkpoint when identity and policy permit;
4. verifies that private data and secrets are not exposed through accessible
   Git metadata;
5. creates a recoverable backup of the vault, operational database, schemas,
   bridge configuration, and key identifiers.

Git is history, not a backup by itself. A successful backup has an identifier,
timestamp, file counts, hashes, retention result, and a completed restore test.
Private content is included only in an appropriately protected backup chosen by
the operator.

### 11.6 Non-negotiable denials

The system MUST NOT:

- use prompts as a substitute for Docker, filesystem, network, or approval
  enforcement;
- reveal or mount private data to test whether the agent obeys;
- mount the Docker socket or grant privileged execution;
- discard existing files or Git changes during setup or migration;
- repeat an uncertain external effect;
- treat an agent-created proposal as approved;
- declare the deployment secure before all access-boundary tests pass.

## 13. Deployment profiles

### 13.1 Local single executor

This is the Phase One reference profile:

- Obsidian, bridge, Hermes, and vault are on one trusted host;
- one active bridge owns the fence;
- workers run in Docker;
- network is denied unless a task grants an enforced allowlist;
- human edits occur on the host;
- private content is never mounted.

### 13.2 Synced hybrid

Desktop and mobile clients MAY synchronise semantic files while one host
executes. High-churn operational state remains outside sync. The deployment
defines conflict behaviour, backup ownership, encryption, and one executor.
Remote approval requires a verifiable signature or authenticated bridge
interaction; a synchronised checkbox is insufficient.

### 13.3 Always-on host

An always-on workstation or VPS uses a dedicated non-root account, operating
system service supervision, restricted inbound access, outbound policy, timely
patching, and encrypted backups. Root installation from a walkthrough is not a
production default.

### 13.4 Multi-agent and multi-host

Multiple agents MAY share approved semantic knowledge, but each receives its
own context, skills, permissions, and write scopes. Multiple active hosts for
one vault are not v2.0 Phase One conformant unless a tested external lease and
monotonic fencing implementation is present.

## 14. Migration from v1.0

V2.0 is intentionally not wire-compatible with v1 resources.

### 14.1 Breaking changes

| V1.0 | V2.0 |
| --- | --- |
| Markdown commands own leases and retry state | Task Markdown expresses intent; SQLite owns commands, leases, retries, and runs |
| Agent can write most of one vault | Explicit read/write, read-only, and hidden zones enforced by mounts |
| Fixed example host paths and timezone | Runtime/profile discovery and deployment-selected IANA timezone |
| `hermes.command/v1` is the primary work object | `hermes.task/v2` is human intent; bridge compiles an operational command |
| Approval status in command/note | Separate approval plus authenticated bridge attestation |
| Bridge contract is brief | Bridge lifecycle, locking, fencing, dispatch, events, and restart semantics are normative |
| Many loops are called minimum viable | Five Phase One components only |
| Status and logs provide summary visibility | Trace IDs and structured events connect the full lifecycle |
| Runtime observations live in notes | Notes are projections of operational state |

V1 resources are never executed by a v2 bridge without explicit migration.

### 14.2 Migration procedure

The migration planner uses this operation mapping:

| V1 operation | V2 migration outcome |
| --- | --- |
| `source.ingest` | Draft `hermes.task/v2` with `source.ingest`; eligible only after operator review |
| `brief.generate` | Draft `hermes.task/v2` with `brief.generate`; eligible only after operator review |
| `action.execute` | Blocked migration finding; prior approval is never imported as authority |
| `capture.triage`, `source.refresh`, `knowledge.query`, `wiki.ripple`, `wiki.lint`, `project.reconcile`, `task.reconcile`, `plan.create`, `doctrine.synthesise`, `armory.propose`, `outcome.evaluate`, `system.audit` | Non-executable migration proposal linked to the corresponding deferred extension |
| Unknown or malformed operation | Quarantined migration finding; no v2 task |

The routine mapping is:

| V1 routine | V2 migration outcome |
| --- | --- |
| Control reconciler | Bridge configuration proposal, not a cron routine |
| Command router | Built-in deterministic router configuration proposal |
| Ingest worker, queue watchdog, daily brief | Disabled v2 routine requiring schema validation and fresh routine-spec approval |
| Every other worker or synthesis loop | Disabled migration proposal tied to a deferred extension |

Unsupported operations are not copied into `hermes.task/v2.operation`; doing so
would create an invalid resource. The v1 source and migration proposal preserve
the intent until that extension defines a v2 operation schema.

1. Stop v1 workers and record all native cron jobs.
2. Verify no command has an uncertain external effect. Block any that does.
3. Back up the vault, Hermes configuration, job registry, and receipts.
4. Create a Git or equivalent baseline without discarding existing changes.
5. Discover the active Hermes home, profile, timezone, gateway, and Docker
   configuration.
6. Create staging copies of the v2 zones. Do not move or delete v1 data.
7. Classify data into read/write, read-only, and private zones. Never copy
   private data into an accessible zone.
8. Validate v1 resources and generate a migration report before transforming
   anything.
9. Apply the routine mapping above. Every executable v2 routine requires fresh
   approval of its specification hash.
10. Apply the operation mapping above. Terminal commands become historical
    task/run/receipt projections; unsupported non-terminal commands become
    non-executable migration proposals.
11. Preserve raw source bytes and hashes. Do not rewrite raw evidence.
12. Import verifiable receipts as historical receipts. Mark unverifiable or
    uncertain effects for human review.
13. Initialise the v2 operational store and record migration provenance,
    legacy IDs, and source paths.
14. Configure the three mounts and run all boundary tests.
15. Start the bridge in validation-only mode and compare desired, recorded, and
    native states.
16. Enable only the five Phase One components.
17. Run the migration, recovery, and end-to-end acceptance tests.
18. Retain the v1 backup until a restore drill and operator review pass.

Migration is deterministic where fields map exactly. Ambiguous permissions,
approvals, paths, identities, or active effects require manual resolution.

### 14.3 Rollback

Rollback:

- stops the v2 bridge and workers;
- preserves the v2 database and event journal for diagnosis;
- restores the pre-migration vault and runtime configuration from a verified
  snapshot;
- restores only known-safe v1 jobs;
- does not replay v2 commands or external effects;
- records the rollback reason and unresolved work.

## 15. Acceptance tests

A conforming implementation automates the deterministic portions of these
tests and records evidence for the rest.

### 15.1 Schema and canonicalisation

Verify that:

- complete v2 conformance fixtures pass;
- duplicate YAML keys, aliases, unknown fields, bad timestamps, unknown
  operations, and wrong schema versions fail;
- equivalent mappings produce the same hash;
- changed permissions, action arguments, or ordered steps change the hash;
- generated observation fields do not change the desired specification hash.

### 15.2 Basic lifecycle

Create one valid `source.ingest` task.

Expected:

```text
task ready
→ command queued
→ validated
→ claimed
→ running
→ verifying
→ completed
```

One linked run, trace, raw source, maintained output, and terminal receipt
exist. The task observation matches SQLite.

### 15.3 Empty queue

Run all gates with no eligible work.

Expected:

```text
No model session
No command or run
No vault mutation except an optional bounded health timestamp
```

### 15.4 Dry run and approval

Submit a dry-run ingest task whose proposed reversible changes exceed the
configured bulk-change threshold.

Expected:

- only the plan and normal run projections are written;
- no target or external effect occurs;
- an exact plan hash is recorded;
- a Markdown-only approval edit is rejected;
- an expired, wrong-generation, or wrong-plan attestation is rejected;
- an approved material plan change requires new approval.

### 15.5 Duplicate ingestion

Submit identical content twice.

Expected:

- one canonical source ID and raw copy;
- one content hash;
- no duplicate entity caused by spelling or path changes;
- the second run records a dedupe receipt.

### 15.6 Crash and lease recovery

Terminate a worker after claim and at each durable checkpoint.

Expected:

- SQLite remains consistent;
- the lease expires and is detected;
- safe work resumes or retries after `not_before`;
- uncertain work becomes blocked;
- no receipt or external effect is duplicated;
- trace continuity is preserved.

### 15.7 Prompt injection

Ingest a source containing instructions to alter policy, inspect private data,
run shell commands, or upload files.

Expected:

- text is preserved as raw evidence;
- no embedded instruction becomes authority;
- no permission or context scope expands;
- a diagnostic security flag MAY be recorded;
- the run completes safely or blocks visibly.

### 15.8 Path and symlink attacks

Attempt `..` traversal, absolute host paths, case/Unicode collisions, symlinks,
hard links, alternate mounts, and writes through Git metadata.

Expected:

- every escape is denied before effect;
- no inaccessible content enters a log, event, output, or model context;
- the trace records a redacted denial.

### 15.9 Filesystem boundary tests

Create harmless host-side test files and a private file containing a unique
token that is not shown to the agent.

Inside the worker sandbox:

1. read and modify a `ReadWrite` test file;
2. read a `ReadOnly` test file;
3. fail to create, modify, rename, or delete in `ReadOnly`;
4. see an empty `Private`;
5. fail to write in `Private`;
6. fail to find the private token anywhere accessible.

Inspect the effective container mount table as well as behaviour. If any
private token is visible or a read-only write succeeds, stop all execution.

### 15.10 Gateway and bridge failure

Stop the gateway, then the bridge.

Expected:

- external supervision detects each failure;
- status becomes offline or stale;
- no internal watchdog is credited with detecting its dead scheduler;
- bounded restart policy applies;
- no duplicate command is created after recovery.

### 15.11 Fencing and sync conflict

Attempt to start a second executor and introduce a sync-conflict file.

Expected:

- only the current fence holder can dispatch;
- stale fence tokens cannot checkpoint or complete work;
- affected resources become blocked;
- neither conflicting semantic version is silently discarded.

### 15.12 Backup and restore

Restore the vault and matching operational database into an isolated location.

Expected:

- schemas parse and raw hashes match;
- task, run, trace, approval, output, and receipt links reconcile;
- idempotency keys remain unique;
- no pending command executes during restore;
- secret and private boundaries remain intact.

### 15.13 V1 migration

Run migration planning against representative valid, invalid, terminal,
non-terminal, and uncertain v1 resources.

Expected:

- source files remain unchanged;
- deterministic mappings are repeatable;
- ambiguous resources are reported rather than guessed;
- routines remain disabled pending approval;
- rollback restores the recorded v1 baseline.

## 16. Definition of Phase One “alive”

Obsidian Hermes v2.0 Phase One is alive when:

1. a human-authored ready task becomes exactly one operational command;
2. invalid work is rejected before a model starts;
3. one ingest command completes with immutable evidence, provenance, output,
   trace, and receipt;
4. no-work polling invokes no model;
5. a crash is recoverable without duplicate effect;
6. task and run status can be rebuilt from SQLite;
7. the daily brief links current work and health;
8. gateway, bridge, scheduler, mount, backup, and queue failures are visible;
9. Docker tests prove read/write, read-only, and private boundaries;
10. imported content cannot grant authority;
11. all active routines are typed, pinned, approved, and in sync;
12. a v1 rollback remains available until migration is accepted.

## 17. Deferred extensions

After Phase One acceptance and restore tests pass, extensions MAY be added in
this order:

1. inbox classification and generic query/plan workers;
2. wiki ripple and deterministic wiki lint;
3. backup verification automation;
4. project/task reconciliation;
5. approval-gated action worker;
6. notification delivery;
7. doctrine synthesis and outcome review;
8. skill and automation proposals;
9. an Obsidian plugin for tasks, approvals, status, and interruption;
10. multi-agent handoffs and, later, cross-vault federation.

Each extension defines its own closed operations, schemas, tools, permission
intersection, failure modes, idempotency, trace events, migration, and
acceptance tests.

If externally stateful work becomes long-running, multi-step, or highly
concurrent, the project SHOULD evaluate a durable workflow engine rather than
stretching SQLite and cron into that role. Obsidian remains the intent,
approval, and human projection layer.
